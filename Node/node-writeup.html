Node — Unauthenticated Flow Editor

I leveraged an exposed Node-RED editor to gain remote command execution inside the container. After landing as an unprivileged user, I discovered a misconfigured SUID binary that loaded a shared library from a user-writable path.

By compiling a malicious C library and uploading it via the flow editor, I hijacked the SUID binary's execution flow and achieved root access.

01 //

Reconnaissance

phase / analysis

I opened the provided instance URL and found a Node-RED flow editor directly exposed to the internet with no authentication prompt. Node-RED allows users to build event-driven applications using visual flows, and crucially, it provides an exec node capable of running operating system commands.

I quickly wired up a temporary flow: an HTTP in node routing to an exec node, and then finally routing the stdout to an HTTP response node. Triggering the endpoint confirmed command execution. Running id showed that the service was executing as the unprivileged node user, which meant I couldn't directly read the flag located in /root.

02 //

Finding Privilege Escalation

phase / enum

Since I needed root access, I searched for SUID binaries on the system using find / -perm -4000 -type f 2>/dev/null. The command returned an interesting custom binary: /usr/local/bin/nodestatus.

Checking its permissions with ls -la confirmed it was owned by root with the SUID bit set. I ran ldd and strings against the binary and made a critical discovery: the binary dynamically loaded a shared library named libshared.so directly from the /var/lib/node/ directory.

A quick permission check of /var/lib/node showed that the node user had write access to this directory. The core bug was glaringly obvious: a SUID-root program was blindly loading a shared library from a user-writable path. If I could replace that library, any code placed inside its constructor would execute with root privileges the moment the binary was invoked.

03 //

Malicious Shared Library

phase / exploit

I wrote a simple C payload for the shared library. Using the __attribute__((constructor)) directive, the init function automatically runs when the library is loaded into memory, well before the main logic of nodestatus even begins.

#include <unistd.h>
#include <stdlib.h>

__attribute__((constructor))
void init(void) {
    setgid(0);
    setuid(0);
    system("cat /root/flag* /flag* 2>/dev/null");
}

void get_status(void) {}
void print_status(void) {}

I included dummy exported functions like get_status just in case the binary rigidly checked for their existence. I then compiled it using gcc -shared -fPIC payload.c -o libshared.so and used my Node-RED RCE setup to execute the deployment sequence: remove the old library, write the new malicious library, fix the permissions, and finally execute /usr/local/bin/nodestatus.

The instant the binary ran, it loaded my library as root, the constructor triggered, and the flag was dumped to standard output.
