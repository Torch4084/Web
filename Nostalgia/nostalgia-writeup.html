Nostalgia: linux vm in a scratch project

A 10 MB Scratch project that contains a complete RV32 Linux machine. The 177 MB JSON inside the .sb3 file looks like an animation, but it is actually a guest ROM stored as a list of decimal strings. The flag is in /root/readme.txt inside an initramfs embedded in the ROM. The challenge is not to reverse the emulator. The challenge is to peel the nested containers and read the guest filesystem directly.

What I actually do: memory-map the 177 MB project.json to find the RISCV.ROM list without parsing the full JSON, convert the decimal strings to raw bytes, identify the resulting rom.bin as a RISC-V Linux image, locate the newc CPIO initramfs at offset 0x191100, parse the 271 archive entries, and cat root/readme.txt.

01 //

triage, what is this 10 MB file

phase / recon

The brief says: "Such old memories ):". I open the file. It's nostalgia.sb3, 10,274,041 bytes. The first recon step is the obvious one: file nostalgia.sb3.

Scratch project files are ZIP archives with a different extension. unzip -l nostalgia.sb3 shows the structure:

$ unzip -l nostalgia.sb3 177433157 project.json 525 2cad5629a7f5460b9df1aae292b686bb.svg 200 3339a2953a3bf62bb80e54ff575dbced.svg 202 cd21514d0531fdffb22204e0ec5ed84a.svg 148 4b7a854341abd530a6780bfb6a68627c.svg 109 e7548d19bd66370776cc24cc625e8217.png 111 19adfcc5dc405c3e48bc3443d6a85412.png 18664 5b73fac1a49ddbb02f856148f44e410e.wav

Six tiny assets (the default Scratch sprite costumes, plus one wav), and one enormous project.json. 177 MB of JSON. Manual block inspection is not happening. The 177 MB is the tell: a real Scratch animation would be 200-500 KB at most. 177 MB is a payload, not animation data.

What is the JSON encoding? The standard Scratch project format stores the script and asset data as a JSON tree. The big fields are usually base64-encoded image and sound data, and the scripts themselves are nested arrays of dictionaries describing blocks. Either of those is the right shape for 177 MB. Either way, looking at the file's first few hundred bytes is enough to confirm the format. But to find what's actually interesting, I need to search the JSON for unusual keys, not parse the whole structure.

The 177 MB is interesting because it's the size of the ROM, but inflated. The JSON must be storing raw bytes as something that costs more bytes per byte than base64 (base64 is 1.33x, plain hex is 2x, decimal strings are up to 3x).
If I parse the whole JSON to find the interesting fields, I'll wait a long time for the JSON parser. If I memory-map the file and grep for markers, I can find the interesting sections in milliseconds.
A mmap + marker search is the right shape for a challenge where the interesting data is wrapped in 177 MB of noise. The challenge is asking me to skip the JSON parse.
02 //

scratch, the stage variables give it away

phase / recon

Before I commit to the mmap trick, I want to confirm the JSON is actually a Scratch project, not just a renamed file with a different structure. I open the first KB or so of project.json and look for the top-level keys.

Scratch project.json has a known shape: "targets" (an array of sprites), "monitors" (an array of stage variable displays), "extensions", "meta". The stage variables are exposed in the monitors array, and a project comment or stage variable often describes the design.

Inside the monitors array, the relevant fields are id and params. The variable names are usually short and tell the whole story. In this case, the stage declares a list of variables that are clearly RISC-V related: RISCV.state, RISCV.kHz, RISCV.ROM, RISCV.DTB, RAM, REG, plus a couple of terminal input/output buffers. A project comment in the same area describes a functional rv32ima emulator intended to boot Linux.

So the project is not a "scratch animation" at all. The scratch blocks are running an RV32 emulator in the project, and the guest's ROM is one of the stage variables. That variable is named RISCV.ROM and it must be the 177 MB.

The trap to avoid: trying to load the project in the actual Scratch editor, or trying to run the emulator and watch it boot Linux. The Scratch VM is slow, the emulator is slower, and the prize at the end of "boot Linux and read the flag" is exactly the same as the prize at the end of "peel the layers and read the flag." The first path takes hours. The second takes seconds.

// the slow path I almost took

Loading a 177 MB JSON in the actual Scratch editor will either take forever or fail. Loading the emulator state in scratch-vm and running the rv32ima core in JS is technically doable but I would have to find a scratch-vm build that supports this much project state, then wait for the emulator to boot. The Peel the layers path is much faster and gives the same answer. The challenge is a forensic one, not a runtime one. The flag is data on disk, not the output of running a guest kernel.

03 //

rom, the 177 MB becomes 4 MB

phase / extraction

The RISCV.ROM list is what I want. It is stored somewhere in the JSON, and it must be where the 177 MB of bulk comes from. The cleanest way to find it without parsing the whole JSON is to memory-map the file and look for the literal ["RISCV.ROM",[ marker.

The marker appears at byte 373 of project.json. The end of the list is at byte 21,113,636. The list itself contains 4,263,000 numeric strings, one per ROM byte. Converting those numeric strings to raw bytes gives 4,263,000 bytes of actual ROM data. So the JSON inflation factor is about 5x. Each byte is stored as a quoted decimal string (e.g. "255" for 0xFF), which means 3-4 characters of source for 1 byte of output. Add the JSON commas and brackets and you get the 5x.

The extraction code is short. Memory-map, find the marker, find the closing ]], regex every "N" in between, convert to int, pack into bytes:

# streaming-style ROM extraction import mmap, re from pathlib import Path project = Path("nostalgia/project.json") output = Path("rom.bin") marker = b'["RISCV.ROM",[' with project.open("rb") as source: data = mmap.mmap(source.fileno(), 0, access=mmap.ACCESS_READ) start = data.find(marker) + len(marker) end = data.find(b']]', start) pattern = re.compile(rb'"([0-9]+)"') rom = bytes( int(match.group(1)) for match in pattern.finditer(data, start, end) ) data.close() output.write_bytes(rom) print(f"wrote {len(rom)} bytes") wrote 4263000 bytes

Output: 4,263,000 bytes of raw ROM. That is a sensible size for a RISC-V Linux image. The first bytes of the output should be RISC-V instructions. I confirm: the first instruction is a typical RISC-V AUIPC (add upper immediate to PC), which is what a real RISC-V bootloader or kernel entry point looks like. The ROM is real, not a placeholder.

04 //

initramfs, parse the newc cpio

phase / cpio

The 4 MB ROM is a RISC-V Linux image. Most embedded Linux images embed the root filesystem as a CPIO archive called an "initial RAM filesystem" or "initramfs." The Linux kernel unpacks the initramfs into a tmpfs at boot and runs /init from inside it. The initramfs format on modern Linux is "newc" (also called "new ASCII format" or just "cpio newc").

The newc format is plain enough. Every file in the archive is preceded by a 110-byte header with 13 fields, each 8 hex characters. The relevant fields are: mode (file permissions and type), size (file data size in bytes), and namesize (filename length including the null terminator). The filename follows the header. File data follows the filename, padded to a 4-byte boundary. The archive ends with a special entry called TRAILER!!!.

The initramfs sits at offset 0x191100 in the ROM. I locate it by grepping for the newc magic, which is the ASCII string 070701:

$ grep -abo '070701' rom.bin | head 1642752:070701 // = 0x191100 1642864:070701 1642980:070701 ... // 273 hits, one per header (some headers are nested)

The CPIO parser is short. Walk forward from 0x191100, parse each 110-byte header, read the filename, read the file data, advance to the next 4-byte boundary, repeat until you hit TRAILER!!!:

# core newc parser def align4(value): return (value + 3) & ~3 cursor = 0x191100 while rom[cursor:cursor + 6] == b"070701": header = rom[cursor:cursor + 110] fields = [ int(header[6 + i * 8:14 + i * 8], 16) for i in range(13) ] mode = fields[1] size = fields[6] name_size = fields[11] name_start = cursor + 110 name = rom[name_start:name_start + name_size - 1].decode() data_start = align4(name_start + name_size) data_end = data_start + size if name == "TRAILER!!!": break # ... write file at data_start..data_end to disk ... cursor = align4(data_end)

The archive contains 271 entries and ends at offset 0x3a22ac. The extracted filesystem is a compact Linux tree with busybox, duktape (a small JS engine), CoreMark (an embedded CPU benchmark), some text-mode games, and an automatic login for the ctf account via inittab:

# recovered guest configuration console::respawn:/bin/login -f ctf ctf:x:1000:100:ScratchB2R!!!:/tmp:/bin/sh

The GECOS field of the ctf user, ScratchB2R!!!, is a nice meta-confirmation: the SB3 (Scratch) file wraps a B2R (board-to-RISC-V) emulator. The user comment is a joke from the author, and the /bin/login -f means the system auto-logs in as ctf on boot.

The interesting file was already present in root's home directory:

$ cat rootfs/root/readme.txt console.log("OmniCTF{ig_bro_have_some_n0stalgiaaa-676767676789}");

And there it is. The flag is a 396-byte file padded with newlines, and the only meaningful content is the one line: console.log("OmniCTF{ig_bro_have_some_n0stalgiaaa-676767676789}");. The 396-byte size is because the file is padded to 4 bytes, but 396 mod 4 = 0, so this is not a padding artifact, it is the full content. The padding is just to the next 4-byte boundary from the previous entry's data_end.

The recovered flag is OmniCTF{ig_bro_have_some_n0stalgiaaa-676767676789}. In l33t, the message is "ig bro have some nostalgia" with the random-looking -676767676789 suffix on the end. The whole flag is a callback to the title of the challenge, with a little extra mystery on the end.

One thing worth noting: the file is 396 bytes because the data is padded to a 4-byte boundary from the previous CPIO entry's data_end. The 396 bytes break down to: 1 line of meaningful content (about 53 bytes of useful text), then about 343 bytes of trailing newlines. The newlines are not meaningful, they are just whatever bytes were in the ROM at the end of the file's data region. The flag is the 53 bytes of meaningful text, not the padding.

The challenge itself is a textbook example of container-in-container-in-container. Each layer has a clear next step: ZIP for the archive, mmap for the JSON, byte list for the ROM, newc CPIO for the initramfs, file path for the flag. The work is in knowing which layer to stop at and not getting stuck trying to boot the guest.
