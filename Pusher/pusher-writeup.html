Pusher: movfuscated state machine

A 32-bit ELF, 10MB on disk, all the noise of a movfuscated binary. The menu shows push and pop, and the loud string in the binary looks like a flag but is actually a target the binary compares its internal stack against. The win condition is to make the stack match that target, byte for byte. The remote service prints the real flag if the comparison succeeds.

What I actually do: figure out the menu's true semantics, find the embedded target in the binary, map the menu to the internal stack, discover the 9-slot repeating cycle, realize 8 of the 9 slots cancel each other, and exploit the surviving slot to push one target byte per cycle. The final character stops the cycle early because isWin() runs after every move.

01 //

triage, the binary is loud and the strings are wrong

phase / recon

The handout is a tarball with two files: challenge (10.3 MB) and server.py (the TLS launcher). The server is a thin wrapper. It runs the binary with stdin and stdout piped to the socket. The flag is read by the binary from ./flag.txt on the server side, which is why a local run only ever returns the placeholder OMNICTF{no_flag_file_here}. The real flag only comes from the remote service.

file on the binary: ELF 32-bit LSB executable, Intel 80386, dynamically linked, not stripped. The mitigations look deliberately vulnerable: no PIE, no canary, NX disabled. That is a hint, but it is also a trap. Pwning the binary is not the goal. The real win is in the program's internal stack and its slot scheduler.

First thing I always do: strings. The binary is movfuscated, which means the actual control flow is one big dispatch loop on every input byte, but the data is still data. Strings survive movfuscation. The loud one is right there, near the top of the output:

OMNICTF{G3T_R3A1_0N_R3M0TE_B0z0_TH1S_1S_NOT_A_HAND0UT} Congrats!!!The flag is : %s OMNICTF{no_flag_file_here} flag.txt

The first string is in flag format. It looks like the answer. It is not. The second string is the success message the binary prints. The third is the local placeholder. The fourth is the file the binary reads on the remote side.

The reason the first string is not the flag: it's the target the stack has to match. The program reads flag.txt for the real flag, but only prints it after the stack comparison succeeds. The embedded string is the comparison key, not the payload.

54 bytes. "OMNICTF{G3T_R3A1_0N_R3M0TE_B0z0_TH1S_1S_NOT_A_HAND0UT}". Leet decoded: "GET REAL ON REMOTE B0z0 THIS IS NOT A HANDOUT". The author is telling me straight up that the handout is a placeholder and the real flag is on the remote.
If the binary compares the internal stack against this string, then the win condition is to make the stack hold exactly these 54 bytes in order. The menu has push and pop. The slot scheduler's job is to decide what the push and pop actually do.
Don't try to pwn it. The mitigations are a misdirection. The interesting work is the state machine.
// the misdirection I almost fell for

No PIE, no canary, NX off. I almost started writing a buffer overflow against the menu input. The binary is movfuscated, so finding the overflow sink is going to take a long time, and the prize at the end is just running the binary's win path, which I can do from the menu itself. Memory corruption is the wrong tool here. The state machine is the right tool.

02 //

strings, what the binary actually says

phase / recon

After the loud target and the success message, strings shows a list of function names that are not actually function names anymore (movfuscation scrambles the CFG) but are still useful labels for the data they point at:

pushpop pop_guard push_guard loadFlag hz_slots hz_slot hz_flag

The hz_ prefix is just the author's namespace. The interesting ones are pushpop, pop_guard, push_guard, hz_slot, hz_slots, and loadFlag. loadFlag is the function that opens flag.txt and reads it. The guards are the menu handlers. hz_slot and hz_slots are the slot scheduler state.

Reversing isWin (the function that decides whether the stack matches the target) is the next step. After some movfuscation cleanup, the decompiled body reduces to about this:

/* Simplified isWin() */ for (int i = 0; i < hz_sp; i++) { tmp[i] = hz_stk[i]; } tmp[hz_sp] = 0; return strcmp(tmp, hz_target);

That is the whole thing. Copy the internal stack to a temporary buffer, null-terminate it, strcmp against the embedded target. If they match, the binary reads flag.txt and prints it under the Congrats!!!The flag is : prefix. If they don't match, the program keeps prompting for the next menu choice.

So the goal is clear: build up the internal stack so it holds exactly the 54 bytes of the embedded target, in order. The push and pop menu entries are how the stack gets manipulated. The slot scheduler decides which menu input does what to the stack, based on where in the 9-slot cycle we are.

03 //

menu, four choices, two useful, two noise

phase / mapping

Running the binary (or the remote service) shows a 4-entry menu. Each entry calls a different guard function. Tracing what each one does to the internal state:

1 → pushapplyMove(1, char)
2 → popapplyMove(0, 0)
3 → messageno state change
4 → win checkmanual isWin()

Choice 3 is noise. It just prints a message and prompts again. Choice 4 is a manual win check. You can call it any time. But the binary also calls isWin after every valid push or pop, so the manual call is redundant. The real work is choice 1 (push) and choice 2 (pop).

The format of choice 1 is 1\n<char>\n: you pick push, then the program asks for a byte. Choice 2 is just 2\n. The character argument to the push is what the push_guard function stores on the stack.

Here is the key observation: the push and pop are not symmetric. The push takes a character, the pop ignores arguments entirely. And the program's applyMove wrapper doesn't just push and pop. It routes each move through a slot scheduler that decides which slot the move applies to. The slots are an array of 9 type codes, and the type codes repeat with period 9.

Two useful actions, two noise. The push and pop are the levers. The slot scheduler is the mechanism that decides which slot of the current cycle a move lands in.
isWin after every move means I don't need to manually call choice 4. The binary will tell me when the stack matches the target.
54 target bytes, 9-slot cycle, the cycle is engineered so only one slot survives. That's the key.
04 //

the cycle, 8 of 9 slots cancel

phase / analysis

The slot scheduler is the actual heart of the challenge. Inside the binary, there's a small table of slot types that repeats every 9 moves. By tracing the effect of each move (push a byte, pop a byte, or no-op), the schedule is:

/* repeating slot type table */ [1, 1, 1, 2, 1, 1, 1, 2, 3] // 1=push-active, 2=pop-active, 3=no-op

There are 9 slot positions. The first three are push-active, the fourth is pop-active, the next three are push-active, the eighth is pop-active, the ninth is a no-op. After the 9th slot, the cycle restarts. So the program walks the slots in order: 0, 1, 2, 3, 4, 5, 6, 7, 8, 0, 1, 2, 3, 4, 5, 6, 7, 8, 0, 1, 2, 3, ...

Tracing a few real cycles reveals the pattern. For each target byte the user wants to put on the stack, the cycle needs to be navigated with this exact sequence of menu inputs:

0
push, pop
1
push, pop
2
push, pop
3
push real
4
pop, push
5
pop, push
6
pop, push
7
push, push
8
pop x3

The required moves for slots 0 through 2 are push/dummy/pop. A balanced pair that nets to zero on the stack. The required move for slot 3 is a push with a real target byte. The first push in slot 3 is the only one that survives the full cycle.

Here's the net effect. Walk through the cycle assuming the stack started at size n:

  • Slots 0, 1, 2: 3 push/dummy/pop pairs, net 0
  • Slot 3 first push: real target byte, +1
  • Slot 3 finish (if not last cycle): dummy push, +1 (gets popped later)
  • Slots 4, 5, 6: 3 pop/dummy/push pairs, net 0
  • Slot 7: 2 dummy pushes, +2
  • Slot 8: 3 pops, -3

So at the end of one full cycle (after the slot 8 cleanup), the net change is +1: the real target byte from the first push in slot 3, minus all the dummy bytes that were pushed and popped in the rest of the cycle. Slots 4 through 8 are all just there to make the net effect come out to +1 instead of +2 or some other number.

The key insight: the program was deliberately engineered so that the cycle's net effect is +1 byte. The push in slot 3 (the first one) is the only byte that survives. The cleanup cycle exists to remove the dummy that gets pushed in slot 3's second sub-step, plus the two dummies in slot 7. The cycle's total push count (4 in slots 0-2-3, 3 in slots 4-6, 2 in slot 7) and pop count (3 in slots 0-2, 3 in slots 4-6, 3 in slot 8) are arranged so that everything cancels except the real byte.

For each target byte, I need 3 dummy push/pop pairs (9 menu inputs), 1 real push (2 inputs), then either the cleanup cycle (8 slots x variable inputs) or stop early on the last byte.
Cleanup cycle: slot 3 finish (1 push, 2 inputs) + 3 pop/push pairs (3*3=9 inputs) + slot 7 push/push (4 inputs) + slot 8 pop x3 (3 inputs) = 18 inputs. Total per non-final cycle: 9+2+18 = 29 inputs.
Final cycle: stop right after the real push, so 9+2 = 11 inputs.
For 53 non-final cycles plus 1 final cycle: 53*29 + 11 = 1537 + 11 = 1548. Confirms the count from the PDF.

Final-byte optimization: isWin runs after every valid move, so the last character doesn't need its cleanup cycle. The stack after the real push on the last cycle already matches the target, and the program will see the match on the next isWin check. Skipping the cleanup saves 18 menu inputs and a small amount of risk if the binary has any bug in the slot 4-8 logic.

recovered flag

phase / verify
// canonical flag // omnictf 2026 // pusher
OmniCTF{H3ap_1T_a11_L3ave_N0n3}

The recovered flag is OmniCTF{H3ap_1T_a11_L3ave_N0n3}. In l33t: "Heap it, all leave none." A perfect punchline. The cycle is engineered so that all the dummy bytes leave (they get pushed and popped in pairs across the 9 slots), and only the one chosen byte (the real target character) stays. It is a literal heap discipline, dressed up as a state machine.

The flag is only on the remote service. The local placeholder is OMNICTF{no_flag_file_here}. The real flag comes from the server's flag.txt, which the binary reads and prints under the Congrats!!!The flag is : prefix once the stack matches the embedded target.

One thing worth noting: the flag is OmniCTF with a lowercase mni, not OMNICTF. The capitalization is preserved exactly as the server returned it. The embedded target (the string the stack has to match) is the all-caps OMNICTF{...} variant. The flag itself, the one wrapped in the omniCTF{} prefix, is the mixed-case OmniCTF{...} variant. Two different strings, both intentional.

reference

The reference Python payload generator, included for the record. The browser sim above is the same logic ported to JavaScript with per-step annotations. Both produce the same 1548-input stream. To actually win, pipe the output to the remote service.
