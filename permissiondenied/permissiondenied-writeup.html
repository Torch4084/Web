01 //

first contact, read the book and count the plugins

phase / recon

Ok so I open the IP play.omnictf.com:25606 in Minecraft 1.21.11 and join. I spawn into a small lobby. There's a book in my inventory. The book is the first real clue. In CTF challenges, free text the game gives you before you do anything is almost always a hint.

The book talks about plugins and that the server owner "didn't want the perms to be broken." Two takeaways: there's custom stuff on the server, and the security model is permissions. Both point at the plugins.

First thing I try is /plugins. That's the vanilla Bukkit/Spigot command to list installed plugins:

[Server] Bukkit Plugins: CTFhandler, GroupManager

Two plugins. CTFhandler is obviously the flag-gating plugin (the challenge name is "permissiondenied", the prefix is CTF, the tip says an auth plugin is unrelated). GroupManager is the classic EssentialsX perm plugin for Bukkit servers. It handles ranks and perms.

The tip also says the server is Bukkit, not Paper. That matters more than it looks. Paper added a bunch of stricter command parsing and disabled a lot of older Bukkit-isms. Knowing it's Bukkit means I can use a few of the older command formats directly.

"Perms not to be broken" = the security model is the GroupManager permissions. The custom demote plugin is a good place to start poking because (a) the title is literally "permissiondenied" and (b) demote affects rank.
The flag-gating plugin is CTFhandler. The flag is almost certainly printed when an admin runs /flag. I need admin.
Bukkit (not Paper) means I can use /bukkit:<plugin> to query plugin internals. GroupManager has a few well-known commands for listing groups and perms.
// the first thing I tried that didn't work

I almost spent five minutes trying to use /version to dig into the plugin metadata. It does print the plugin list with version strings and authors, but it doesn't tell you what commands each plugin registers. The writeup I was referencing later said the same thing: /version is "not as useful because it doesn't tell me about the commands each plugin has." The actual path is to ask Bukkit directly.

02 //

recon: the bukkit:$ trick and groupmanager commands

phase / recon

On a Bukkit server, there's a hidden command format you can use to interrogate any plugin: /bukkit:<plugin>. It falls through to the plugin's own command handler, which for GroupManager prints the help text.

/bukkit:$ groupmanager
---------- Help: GroupManager ----------
Below is a list of all GroupManager commands:
/manglist: Lists all groups available.
/manglistp: Lists all permissions of a group.

Two commands. I run /manglist first:

/manglist
Groups available:
  Admin, Builder, Default, Helper, Limited, Moderator, Prisoner, Restricted

Eight groups, ordered bottom-to-top: Prisoner (0) → Restricted (1) → Limited (2) → Default (3) → Builder (4) → Helper (5) → Moderator (6) → Admin (7). The /demote help text I see later confirms this index mapping.

I'm currently Default (rank 3, the lobby default). The challenge is to get to Admin (rank 7). I run /manglistp default to see what permissions a default-rank player actually has:

/manglistp default
The group 'Default' has the following permissions:
-bukkit.command.kill, -essentials.*, -pluginhider.*,
bukkit.command.plugins, customdemotion.demote, groupmanager.manglist, groupmanager.manglistp
And all permissions from groups: g:groupmanager_default, g:bukkit_default, g:essentials_default

Four things I notice in this list:

  1. The - prefix means "explicitly denied", so Essentials and the kill command are turned off. That's normal for a default rank.
  2. bukkit.command.plugins is the only granted vanilla Bukkit command. That's how I listed the plugins earlier.
  3. groupmanager.manglist and groupmanager.manglistp are granted, which is why I can inspect perms at all.
  4. customdemotion.demote. A custom plugin called CustomDemotion has granted the default group a demote permission. There is no matching customdemotion.promote.
Why is demote granted to default but not promote? In a normal server, a default-rank player shouldn't be able to demote themselves OR promote themselves. Granting demote alone is weird.
Two possibilities: (a) the demote is meant to be self-only and the plugin handles it safely, or (b) the demote command is the way you change rank in this server, full stop, and the only question is which direction you can go.
If (b), there are two sub-possibilities. The demote command might be a one-way trip down the ladder (with a hardcoded check that prevents upward moves), or it might just be "set your rank to <index>" with the author having only tested it with downward values.
Time to read the demote help text and try things.
03 //

the exploit: negative indices and signed underflow

phase / exploit

I type /demote with no arguments to see the help text:

/demote
Usage: /demote <index>
Available ranks:
  0 -> Prisoner
  1 -> Restricted
  2 -> Limited
  3 -> Default (current rank)
  4 -> Builder
  5 -> Helper
  6 -> Moderator
  7 -> Admin

Eight ranks, indices 0..7. The natural thing to try first is /demote 7, to ask to be moved to Admin:

/demote 7
You cannot demote yourself above your current rank.

Blocked. The plugin checks that the requested rank is not above my current rank. From Default (3) it would have let me go down to Prisoner (0), Restricted (1), Limited (2), or back to Default (3). It refuses Admin (7).

This is the moment where I started trying negative numbers. The <index> in the help text is just an int. Java's int is signed, so the parser will happily accept negative values. The plugin probably rejects them, but I have to test that. The cost of a single wrong command is a chat message, not a kick from the server.

I run /demote -1, then /demote -2, and so on:

/demote -1
You cannot demote yourself above your current rank.
/demote -2
You cannot demote yourself above your current rank.
/demote -3
You cannot demote yourself above your current rank.
/demote -4
Your rank has been updated to Admin (index: 7).
You were moved to the group Admin in world world.

That's the exploit. /demote -4 puts me in Admin.

The exact mechanism is the classic signed-integer underflow. The plugin almost certainly does one of these:

  • Look up the rank by index in an array of 8 elements: ranks[idx]. If idx is -1, you read one element before the start of the array, usually some other rank's name or null. If idx is -4, you read four elements before, which on a typical Java object layout lands somewhere in the object's header / class pointer area.
  • Mask the index modulo the size: idx & 7. With 8 ranks, -1 & 7 = 7 (Admin), -2 & 7 = 6 (Moderator), -3 & 7 = 5 (Helper), -4 & 7 = 4 (Builder). That doesn't match my observation of getting Admin on -4, so it's probably not a simple bitmask.
  • Add the size to negative indices then look up: if (idx < 0) idx += 8;. That maps -1 → 7, -2 → 6, etc. Doesn't match either.
  • Cast through other types (byte, short) where -1 becomes 255, then take mod 8. -1 → 255 mod 8 = 7 (Admin). -2 → 254 mod 8 = 6. Doesn't match.

The actual code is on the server, which is closed, so I can only infer. The empirical result is: /demote -4 lands on Admin (index 7). The check "cannot demote yourself above your current rank" only fires for negative indices between -3 and -1, which is the only piece of validation the plugin does. Past that, the lookup happens, and whatever the negative index resolves to is what I get.

Wait. The plugin says "cannot demote yourself ABOVE your current rank" for -1, -2, -3 but not for -4? That implies the rank comparison is doing something funky with negatives too. Maybe it's comparing with a signed < 0 check that fails for -4 but passes for -1/-2/-3 due to some Java signed/unsigned mismatch.
Or maybe the check is `if (idx < 0) return errorMsg;` for -1, -2, -3 but the array index out of bounds check catches them and they all error, while -4 happens to land in a memory region that contains the string for the Admin rank.
Either way, the working exploit is /demote -4. The mechanics are an exercise for the reader. Time to grab the flag.

Once I'm Admin, the original gate lifts. That gate was the CTFhandler plugin blocking /flag for non-admins. I type /flag:

/flag
Ouch! You got me there, I guess I should've been more careful when coding my own plugins.
Here's your reward, I guess: OmniCTF{y0U_ar3_a_p3rm1ss1on5_pr0_gw4rf23}

Flag in hand. The plugin author's in-character quip is the end of the chain.

// what I tried that didn't work first

I almost went down the path of trying to use the Essentials /eco or /pay commands to trigger a different code path. The -essentials.* in the default perms means every Essentials command is denied, so this would have been a dead end. I also briefly thought about poking at the pluginhider permission. That plugin's job is to hide plugins from the /plugins output, and the fact that it's wildcard-denied is just a side effect of the author not wanting players to see it. Not the attack surface.

The actual vuln is much smaller and more obvious: the demote command, the only thing the custom plugin does, has a one-line input validation gap. That's the whole challenge.
